# 3.20.0 Auvik cables Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Import from Auvik (web) also brings cables: port-to-port links from Auvik's interface inventory, device-level fallback links marked "no port data", and endpoints that move from the import's own boxes onto their switch.

**Architecture:** A new server route `GET /api/auvik/tenants/:id/links` (same proxy rules as inventory) returns one row per cable. The browser reads it after each site's inventory, turns the rows into `AuvikDevice.neighbors`, and the existing `buildLinks` → `resolvePlan` → `computeDiff` → `applyInPlace` pipeline draws the cables. A small API-only rule decides which endpoints may attach to a switch.

**Tech Stack:** Rust axum + reqwest (web/server), React + TypeScript (rackwright-tauri/src), tests via `cargo test` (CI only, no Rust on this PC) and `npx tsx scripts/*.test.ts`.

**Spec:** `docs/superpowers/specs/2026-11-19-auvik-cables-design.md` (read it first; it builds on `2026-11-18-auvik-api-import-design.md`).

## Review Focus

- Auvik lists a cable on both interfaces (A→B and B→A): exactly one cable, not two.
- An interface whose `connectedTo` points to an interface in another tenant / not in the list: dropped and counted, no panic, no cable to nowhere.
- Two cables between the same two switches (LAG members): two cables on the right port pairs, not crossed and not merged.
- An endpoint the person moved by hand into their own group, or into another rack document: never moved by the import.
- Links read fails (502/timeout/denied) after inventory succeeded: devices still import, one note line, Stop still works.

**Interfaces:**
- Produces (HTTP): `GET /api/auvik/tenants/:id/links` → `{"status":"ok"|"denied"|"empty","note":str,"links":[{"device":str,"iface":str,"peerDevice":str,"peerIface":str,"portless":bool}],"dropped":number}`. Device ids are the same ids as inventory `devices[].id`. Order: sorted by `(device, iface, peerDevice, peerIface)` so the fixture comparison is stable.
- `expected-links-main.json` is the exact response for tenant 1001 and is read by Task 2's tests.

Auvik shapes (from the public spec): interface item `{id, type:"interface", attributes:{interfaceName, interfaceType, ...}, relationships:{parentDevice:{data:{id}}, connectedTo:{data:[{type:"interface", id}]}}}`; device detail `relationships.connectedDevices.data:[{id, type:"device", attributes:{deviceName}}]`.

Rules (`read_links`):
- Kept interface types: `ethernet`, `optical`, `inferredWired`. Aggregates `ieee8023AdLag` / `linkAggregation` are not cables themselves; all other types are dropped.
- A pair (i, j) is emitted once when both are kept types and both are in this tenant's interface list; key = sorted (i.id, j.id). `device`/`iface` is the end with the smaller interface id.
- Aggregate-only LAG: if an aggregate interface pair (both ends aggregates) has a connection and no member pair between the same two devices exists, emit one row with empty ifaces and `portless: true`. Otherwise drop it silently (members carry it).
- Anything else that ends on a dropped type or an unknown interface id: `dropped += 1` (count each pair once).
- Fallback: each `connectedDevices` pair (both ids in this tenant's device detail list, A≠B) with no emitted row between A and B in either direction → one row, ifaces `""`, `portless: true`; deduplicate A→B / B→A.
- 401/403 on the interface list → `{"status":"denied","note":"Auvik denied access to this site's cables.","links":[],"dropped":0}`; no interfaces and no fallback rows → `"empty"` with note `"Auvik lists no connections for this site."`. Other failures → 502 fixed message, like inventory. Same `INVENTORY_TIMEOUT_SECS` cap, same id validation, same `no_store`.

Fixture content (tenant 1001, devices from the existing main fixture, e.g. EX-SW01, EX-SW02, EX-FW01, a printer, a PC): two pages via `links.next` with `{HOST}`; EX-SW01 1/1/1 ↔ EX-FW01 X1 listed on both sides; EX-SW01 1/1/47 + 1/1/48 ↔ EX-SW02 1/1/47 + 1/1/48 as LAG members plus the two aggregates connected to each other; a printer `inferredWired` ↔ EX-SW01 1/1/5; one `wifi` and one `vlan` connection (dropped); one connection to an interface id not in the list (dropped); one `connectedDevices` pair with no interface link (portless).

**Interfaces:**
- Produces: `export interface AuvikLink { device: string; iface: string; peerDevice: string; peerIface: string; portless: boolean }`, `export interface AuvikLinks { status: "ok" | "denied" | "empty"; note: string; links: AuvikLink[]; dropped: number }` in `api.ts`.
- Produces: `linksToNeighbors(devs: AuvikDevice[], links: AuvikLink[]): { unresolved: number; portless: { a: string; b: string }[] }` in `links.ts` — mutates `devs[].neighbors` (matched by `apiId`); `portless` lists device-to-device port-less pairs by display name.
- Produces: `planSite(inv, tenant, siteDocs, defaults, fill, layout?, hosts?, over?, links?)` — `links` last, optional; without it behaviour is exactly 3.19.2.
- Produces: the constant `NO_PORT = "no port data"` exported from `links.ts`.

Neighbour order: process links in the response order; for each, push `{name: B.rawName, iface: peerIface}` onto A and `{name: A.rawName, iface: iface}` onto B. This keeps `buildLinks`' in-order pairing aligned for several cables between one pair. A port-less device-to-device link (neither end an endpoint/VM after classification) adds no neighbour; it is returned in `portless` and shown as a plan warning `"<A> and <B> are connected (no port data)"`. A port-less link to an endpoint adds a neighbour with `iface: ""` (the endpoint joins the switch's group with no port, shown as "no port data").

**Interfaces:**
- Consumes: Task 2's neighbours and `NO_PORT`.
- Produces: `endpointPorts(parsed: ParsedAuvik, items: PlanItem[]): Map<string, { sw: string; port: string; attach: boolean }>` — key = item key of each endpoint-mode item that has a switch neighbour; `attach` false when that switch port also has a switch/router/firewall neighbour, or when two or more endpoints list that same switch port.

Behaviour (spec "Endpoints in the import's own boxes"):
- In `planSite`, before `resolvePlan`, clear the neighbours of endpoints whose `attach` is false (so the plan leaves them unplaced).
- Endpoints with `attach` true and not held elsewhere: the plan's "Endpoints on <switch>" group takes them (new ones are added there, not into a box).
- A member already in an `auvik_epbox` box whose plan now puts it in a group: one change titled `Move to Endpoints on <switch>`, `defaultOn: true`. Ticked → removed from the box and placed in the group with its cable. Unticked → stays in the box; the group does not add it a second time.
- A member in any other box (hand-made group, older .xlsx group, another rack document): no move change, never moved (today's `heldElsewhere` rule).
- `fillEndpointBoxes` writes `port` = `"<switch> <port>"` for box members with a known port (attach false, or move unticked), and `NO_PORT` for a port-less switch link. Empty box after moves → removed.
