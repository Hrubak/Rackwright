# Word report (3.18.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Export the client report as a Word document built into an admin-uploaded master template, with text markers filled anywhere in it.

**Architecture:** Three pure modules under `rackwright-tauri/src/report/` (markers, body XML, packaging) that run under `npx tsx`, plus a browser-side exporter that renders diagrams to PNG and hands them to the packager. The template is a new branding asset `word_template` (server SQLite asset on the web, IndexedDB on the desktop). jszip edits the .docx; untouched parts keep their bytes.

**Tech Stack:** TypeScript, React 18, jszip 3.10.2, fast-xml-parser 5.12.1 (tests only), Rust axum server (CI-compiled only).

**Spec:** `docs/superpowers/specs/2026-11-18-word-report-design.md` — read it before your task; it is the source of truth for copy and behaviour.

## Global Constraints

- No new npm dependency.
- Pure modules (`docxMarkers.ts`, `docxBody.ts`, `docxPackage.ts`) must not import `backend.ts` (`IS_WEB` crashes under tsx), React, or use `document`/`DOMParser`.
- UI colours only via `v(token)`; any literal hex carries `// theme-ok`.
- Tests and fixtures use made-up names only: "Example IT", "Example Client", "EX-SW01". Never real company or customer names.
- Never commit `.superpowers/` or `public/`. Do not commit at all; the controller commits. Write `task-N-report.md` in `.superpowers/sdd/3.18.0-word-report/` when done.
- Do not dispatch subagents.
- Run commands from `rackwright-tauri/`. Tests: `npx tsx scripts/<name>.test.ts`, pattern of `scripts/report.test.ts` (an `eq` helper, `fail` counter, `process.exit(fail ? 1 : 0)` at the end).
- Copy strings exactly as in the spec, including: "The {{RACKWRIGHT}} marker shared a paragraph with other text. That paragraph was replaced by the report." / "The template has no {{RACKWRIGHT}} marker, so the report was added at the end." / "No Word template is uploaded, so this uses plain Word styles. An admin can upload one in Settings › Branding." / "This diagram could not be drawn."
- Word mime: `application/vnd.openxmlformats-officedocument.wordprocessingml.document`.

## Review Focus

1. Runs holding `<w:tab/>`, `<w:br/>`, `<w:fldChar>` or `<w:instrText>` between the pieces of a split marker: only `<w:t>` text changes; tabs, breaks and field codes survive; a `{{CLIENT}}` inside `<w:instrText>` is left alone. (Task 1 test `non-text run children survive`.)
2. Values with `&`, `<`, quotes, an emoji and a newline in inline markers (`{{CLIENT}}` = `"Example & Sons <EU>"`): escaped, emoji kept, newline becomes `<w:br/>`. (Task 1 test `escaping inline values`.)
3. A template whose last paragraph carries its own `<w:sectPr>` inside `<w:pPr>` (section break) plus the body-level `<w:sectPr>`: a missing `{{RACKWRIGHT}}` appends before the body-level one only, and `pageBox` reads the body-level one. (Task 1 `append before body sectPr`, Task 2 `pageBox uses body sectPr`.)
4. A marker in an outer paragraph that also contains a text box with its own paragraphs: the outer paragraph's text does not include the text box text, and each is replaced independently. (Task 1 `nested paragraphs`.)
5. A Detailed report with many racks and one failed diagram: every relationship id and `docPr` id unique, the missing picture becomes "This diagram could not be drawn.". (Task 3 `many pictures, one missing`.)

```ts
export type MarkerName = "CLIENT" | "SITE" | "DATE" | "REPORT_TITLE" | "PREPARED_FOR" | "PREPARED_BY" | "SUMMARY" | "RECOMMENDATIONS" | "RACKWRIGHT";
export type MarkerValues = Record<Exclude<MarkerName, "RACKWRIGHT">, string>;
/** XML-escape & < > " ' and drop characters XML 1.0 forbids (keeps \t \n \r and all of U+0020+ except U+FFFE/U+FFFF and lone surrogates). */
export function xmlText(s: string): string;
/** "2026-11-18" -> "November 18, 2026"; anything not YYYY-MM-DD comes back unchanged. */
export function longDate(iso: string): string;
/** Values from the report model: CLIENT = model.client.name, SITE = model.sites names joined ", ", DATE = longDate(model.date), REPORT_TITLE = model.title, PREPARED_FOR = model.preparedFor, PREPARED_BY = model.preparedBy, SUMMARY = model.summary, RECOMMENDATIONS = model.recommendations. */
export function markerValues(model: ReportModel): MarkerValues;
/** Marker names found in a part's <w:t> text (split runs included), ignoring anything inside <mc:Fallback>. */
export function scanMarkers(xml: string): Set<string>;
export interface ReplaceResult { xml: string; rackwright: "alone" | "shared" | "missing" }
/** Replace every {{NAME}} ([A-Z0-9_]+) in the part. body = WordprocessingML block XML to put at the first {{RACKWRIGHT}} (omit for headers/footers/notes: the marker is then just removed and the result is "missing"). */
export function replaceMarkers(xml: string, values: MarkerValues, body?: string): ReplaceResult;
```

Rules (from the spec, "Marker replacement"): paragraph by paragraph including nested ones; a paragraph's text is only its own `<w:t>` (not those of nested paragraphs); replacement goes into the first run the marker touches; marker characters cut from later runs; emptied `<w:t>` removed; `xml:space="preserve"` added when text has leading/trailing whitespace; unknown or empty-valued markers removed; inline multi-line values become `<w:br/>`-separated text in that run; `{{SUMMARY}}`/`{{RECOMMENDATIONS}}` alone in a paragraph → one paragraph per line, each `<w:p>` + original `<w:pPr>` + one `<w:r>` with the first run's `<w:rPr>`; `{{RACKWRIGHT}}`: first one wins (later ones removed), alone → paragraph replaced by `body`, shared → whole paragraph replaced by `body` and result `"shared"`, inside `<mc:Fallback>` → removed and not counted; missing with `body` given → `body` inserted before the last `<w:sectPr` that is a direct child of `<w:body>` (else before `</w:body>`), result `"missing"`. Everything outside changed `<w:t>` elements and replaced paragraphs stays byte-identical.

Approach (builder's choice, suggested): a tag-level scanner (regex over `<[^>]+>` tokens) that tracks a stack of open `<w:p>` elements and collects, per paragraph, the `<w:t>` token positions; then apply edits from the end of the string backwards. Do not round-trip the part through a DOM or fast-xml-parser.
